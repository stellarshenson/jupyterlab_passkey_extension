# jupyterlab-passkey
Runs on Jupyter server machine. `vault`: server-kept encrypted passwords, unlocked by passkey, unlock password with authenticator code, unlock password with passkey with no PRF (Password and passkey: password decrypts, server checks passkey), or recovery passphrase; git's credential helper reads it. Bridge (`passphrase`, `copy`, `show`, `create`, `get`): one secret, browser to local process. Help: `jupyterlab-passkey --help`, `jupyterlab-passkey vault <command> --help`. Read first.

## Rules

- Every command takes `--json`, after the subcommand and before `--` on `vault exec`; always pass it. stdout is one object, `{"ok": true, "command", "result"}` with exit 0, or `{"ok": false, "command", "error", "code"}` with exit 1; stderr stays empty. Read `result`; on failure `code` is `locked`, `denied`, `entry-not-found`, `invalid`, `conflict`, `no-action`, `server`, or the local `no-vault`, `no-server`, `relay`, `usage`
- Output enters transcript: never `vault get` to screen. Value to command: `vault exec`; to user: `vault copy` or `vault show`. Generic `copy`/`show` require `--label NAME`, secret's name
- Python keeps value in-process: `from jupyterlab_passkey_extension.vault import Vault; Vault().get("github/api")`. Refusal raises `VaultClientError` (`jupyterlab_passkey_extension.vault.client`), `.code` the stable name above; `--json` reports it as `code`
- Never secret on command line. `--in-browser`: vault decides fields by secret kind: two matching when setting a recovery passphrase, else one. `passphrase` asks once; you decide `--twice` when setting one. Agent shell has no hidden-prompt terminal
- Tell user before waiting command. Locked vault, passkey step or dialog raises notification; command blocks until a click. Parallel commands share one unlock notification: one click releases all. After unanswered unlock notification, a command needing unlocked vault fails at once for 10 minutes, naming `jupyterlab-passkey vault unlock`; it still asks. Not proof of a vault: run `jupyterlab-passkey vault status --json`, check `result.initialized` and `result.unlocked` before calling it locked. Notification starts `**<caller>**:`, entry name bold: always pass `--caller "<your project>"` after subcommand; every subcommand takes it; before `--` on `vault exec`, else it goes to command; Python sets `JUPYTERLAB_PASSKEY_CALLER` before `Vault()`; the old `JLAB_PASSKEY_` environment variable names are still read, after the new `JUPYTERLAB_PASSKEY_` names; default project directory, never another project's name
- CLI posts only to the lab its environment names: `JUPYTER_SERVER_URL` (with `JUPYTER_SERVER_ROOT`) or `JUPYTERHUB_SERVICE_PREFIX`, which JupyterLab terminal sets, else `JUPYTER_PORT`. Never unset them or point `JUPYTER_PORT` at another server. `no running Jupyter server matches` or `cannot tell which running Jupyter server is the lab`: tell user, ask which lab; never pick port yourself
- No vault: `vault status --json` answers `result.initialized` false and `result.path`; `list`, `get`, `add`, `edit`, `rm`, `copy`, `show`, `exec`, `import`, `passkey rm`, `git migrate` offer set-up at terminal; git helper with no terminal offers it in page; else the command fails with code `no-vault`, naming `vault init`. An initialized empty vault is unlocked, normal: `result.unlocked` true, `vault list --json` answers an empty `result.entries` and exits 0, panel: `No entries yet.`; never call absent or empty vault locked
- `vault status --json` gives the state: `result.initialized` false is no vault (create: `vault init`, or answer set-up notification); `result.unlocked` false is locked (unlock: `vault unlock`, or panel); true with `result.remaining` seconds is use. A `locked - nobody answered within Ns` error is one per-user record, shared by all that user's servers and vault paths, so it can name another vault: check `result.initialized` first
- Never ask recovery passphrase in chat: `vault unlock --recovery --in-browser --json`; a read command on a locked vault takes `--recovery --in-browser` or `--password --in-browser`, so the agent supplies the method and the user types the secret

## Git credentials

- Set up: `jupyterlab-passkey vault git migrate --json` imports git's plaintext store, prints no secret, puts `jupyterlab-passkey` first in global `credential.helper`, which git runs as `git-credential-jupyterlab-passkey`; nothing to import, `vault git install --json`; undo: `vault git uninstall --json`
- Check: `git config --get-all credential.helper` lists `jupyterlab-passkey` first; `printf 'protocol=https\nhost=github.com\n' | git credential fill` answers matching entry's `username=` and `password=`
- Matching by url host, path only under `credential.useHttpPath`; helper follows gitcredentials(7); `vault git migrate --dry-run --json` lists without writing; `--remove-source` asks at terminal before deleting plaintext file, which stays without it; `JUPYTERLAB_PASSKEY_GIT_IGNORE_VAULT=1` makes the helper answer no credential, so git uses its next helper or prompts; testing aid, not a security control; read by the git helper only, not the CLI or the AWS helper
- A git command can block on user the same way; tell them first

## AWS credentials
- `vault add aws/<profile> -u <access-key-id> --json` stores the key id and secret key; `vault aws install <profile> --json` writes `credential_process` through `aws configure set`; the helper prints the credential-process JSON; a locked vault raises the unlock notification and `aws` waits; static keys only, SSO and azlogin session profiles bypass it; `vault aws uninstall <profile> --json` removes the line
